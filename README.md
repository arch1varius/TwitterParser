# Twitter Parser

Сервер ASP.NET Core 10 с PostgreSQL, сбором страниц X через Playwright и тестовым клиентом WinUI 3. Клиент работает только через HTTP API. MAUI не используется.

## Возможности

- Фоновые задания сбора публикаций автора за период, прогресс и отмена.
- Сохранение полного текста постов от 10 слов, включая ответы, репосты, цитаты и посты с видео/GIF. Изображения, видео и animated GIF не скачиваются.
- Сбор вкладок профиля и ответов с устранением дубликатов. У репоста сохраняется полный текст оригинала под ID, автором и датой репоста; цитируемая запись не импортируется отдельно от поста с цитатой.
- Повторный сбор не создаёт дубликаты. Старые посты в состоянии `PendingPhotos` при повторном импорте становятся готовыми без скачивания фотографий.
- Просмотр сохранённых постов с пагинацией и случайный пост за период.
- Восстановление прерванного задания после перезапуска сервера.
- Необязательная очистка по сроку хранения; по умолчанию срок не ограничен.

## Требования

- .NET SDK 10; `global.json` допускает установленный SDK ветки 10.0.
- PostgreSQL 17 или совместимый актуальный сервер. Для Docker предусмотрен [compose.yaml](compose.yaml).
- Для WinUI: Windows x64, средства разработки Windows / Windows SDK и Visual Studio с поддержкой .NET 10. Windows App SDK поставляется вместе с клиентом.
- Для сбора: Chromium из Playwright и авторизованная серверная сессия X.

## PostgreSQL

Корневой `.env` оставлен пустым для локальных настроек. Заполните его по образцу [.env.example](.env.example): задайте `ConnectionStrings__Parser` и, для Docker, `POSTGRES_PASSWORD`. Пароль в обоих значениях должен совпадать. API автоматически читает `.env` при запуске, включая режим `--login-x`.

Для Docker выполните:

```powershell
docker compose up -d
```

БД `twitter_parser`, пользователь `parser`, адрес `localhost:15432`. Данные сохраняются в Docker volume. `.env` исключён из Git. Для уже созданной БД укажите её действующий пароль: изменение `.env` не меняет пароль в существующем Docker volume.

Если Windows возвращает `ports are not available` / `bind: ... forbidden by its access permissions`, проверьте резервирование портов командой `netsh interface ipv4 show excludedportrange protocol=tcp`. Выберите свободный порт вне исключённых диапазонов, укажите его в `compose.yaml` слева от `:5432` и в строке подключения API. На этой машине прежний порт `54329` попал в исключённый диапазон `54300–54399`; поэтому используется `15432`.

Можно использовать уже установленный PostgreSQL: создайте отдельные БД и пользователя с правами на схему приложения. Строка подключения передаётся через переменную окружения:

```powershell
$env:ConnectionStrings__Parser = 'Host=localhost;Port=15432;Database=twitter_parser;Username=parser;Password=YOUR_PASSWORD'
```

Миграции применяются при запуске API. База данных должна существовать. При недоступной БД сервер не запускается с частично готовой схемой.

## Сборка и запуск

Из корня решения:

```powershell
dotnet build Parser.slnx -p:Platform=x64
pwsh src/Parser.Api/bin/Debug/net10.0/playwright.ps1 install chromium
```

Для сборки Release замените `Debug` на `Release`. При отдельной сборке проекта с явно заданной платформой путь может дополнительно включать `x64`.

Один раз выполните вход в X на машине сервера:

```powershell
dotnet run --project src/Parser.Api -- --login-x
```

Откроется браузер. Завершите вход и нажмите Enter в терминале. Команда проверяет наличие сессионной cookie и сохраняет состояние браузера в каталоге данных. Сам пароль не сохраняется. Состояние содержит секреты сессии: не отправляйте его клиентам и не добавляйте в Git.

Если вход через Google в окне Playwright блокируется, можно передать действующую сессию своего аккаунта X. В обычном браузере, где вы уже вошли в `https://x.com`, откройте DevTools (F12) → Application / Приложение → Storage → Cookies → `https://x.com`. Скопируйте **значение** cookie `auth_token`; при необходимости также `ct0` из той же сессии. Это cookie X, а не токен Google или API Bearer token.

Для постоянной настройки добавьте значения cookie в корневой `.env`:

```dotenv
Parser__AuthToken=YOUR_X_AUTH_TOKEN
Parser__CsrfToken=YOUR_X_CT0
```

`Parser__CsrfToken` можно оставить пустым. После заполнения `ConnectionStrings__Parser` и cookie достаточно команды `dotnet run --project src/Parser.Api` без предварительного ввода переменных в терминале. Для диагностики загрузки профиля задайте в `.env` `Parser__Headless=false` и, при необходимости, `Parser__ScrollDelayMs=10000`.

Альтернатива на один запуск в PowerShell 7 — передать значения через скрытый ввод:

```powershell
$env:Parser__AuthToken = Read-Host 'auth_token из X' -MaskInput
$env:Parser__CsrfToken = Read-Host 'ct0 из X (Enter, чтобы пропустить)' -MaskInput
try {
    dotnet run --project src/Parser.Api
} finally {
    Remove-Item Env:Parser__AuthToken, Env:Parser__CsrfToken -ErrorAction SilentlyContinue
}
```

В этом режиме `--login-x` не нужен. `Parser:AuthToken` имеет приоритет над файлом `Parser:StorageStatePath`: сохранённая сессия не загружается и не перезаписывается, переданные cookie используются в памяти браузера. `Parser:CsrfToken` необязателен и используется только вместе с `Parser:AuthToken`. Если без `ct0` вход не работает, передайте обе cookie из одной действующей сессии. Проверка действительности сессии происходит при сборе, а не при запуске API; истёкшая сессия или дополнительная проверка X всё ещё могут привести к `NeedsLogin`. Тогда обновите значения и перезапустите API. Строка подключения к PostgreSQL и установленный Chromium по-прежнему необходимы. Не публикуйте cookie и не добавляйте их в Git: они предоставляют доступ к аккаунту.

Если используется сохранённая через `--login-x` сессия, запустите сервер:

```powershell
dotnet run --project src/Parser.Api
```

По умолчанию адрес `http://localhost:5080`. WinUI-клиент запускается отдельным процессом:

```powershell
dotnet run --project src/Parser.WinUI -p:Platform=x64
```

В клиенте проверьте подключение, укажите username и период, запустите сбор. ID задания можно сохранить и вставить после перезапуска клиента. Во вкладках просмотра и случайного поста выберите сохранённого автора. Даты интерфейса включают оба выбранных дня и переводятся в UTC с учётом локального часового пояса.

## Настройки

Настройки находятся в [appsettings.json](src/Parser.Api/appsettings.json). Локальные значения можно задать в `src/Parser.Api/appsettings.Local.json`, корневом `.env` либо переменных окружения: `:` заменяется на `__`. Приоритет по возрастанию: JSON → `appsettings.Local.json` → `.env` → переменные окружения. Локальные файлы исключены из Git; `.env.example` содержит только шаблон. Ранее заданные `$env:Parser__AuthToken`, `$env:Parser__CsrfToken` и другие переменные перекрывают файл: удалите их через `Remove-Item Env:ИМЯ` или откройте новый терминал, чтобы использовать значения из `.env`.

В исходном проекте `.env` ищется рядом с `Parser.slnx`, независимо от запуска из корня или `src/Parser.Api`. При запуске опубликованного приложения вне дерева исходников файл читается из content root приложения. Отсутствующий или пустой `.env` допустим, но обязательную строку подключения нужно задать другим способом. Файл читается один раз: после изменения перезапустите API.

Формат: `KEY=value`, пустые строки, комментарии `#`, необязательный префикс `export`, одинарные или двойные кавычки вокруг значения. Комментарий после значения отделяйте пробелом. Значения однострочные; содержимое кавычек сохраняется буквально, без подстановки `${VARIABLE}` и escape-последовательностей. В строке подключения указывайте полный пароль, а не `${POSTGRES_PASSWORD}`. Для значения с `$` используйте одинарные кавычки, чтобы Docker Compose также не выполнял подстановку. Ошибка формата показывает номер строки без её содержимого.

| Ключ | По умолчанию / назначение |
| --- | --- |
| `ConnectionStrings:Parser` | Обязательная строка подключения PostgreSQL |
| `Urls` | `http://localhost:5080` |
| `Api:Key` | Пусто; при заполнении все запросы требуют заголовок `X-Api-Key` |
| `Api:AllowAnonymousLoopback` | `true`; без ключа разрешены только подключения с loopback-адреса |
| `Parser:DataDirectory` | `%LOCALAPPDATA%/TwitterParser` на Windows; каталог локальных данных пользователя на других ОС |
| `Parser:StorageStatePath` | По умолчанию `storage-state.json` в каталоге данных |
| `Parser:AuthToken` | Не задан; значение cookie X `auth_token`, при заполнении заменяет сохранённую сессию |
| `Parser:CsrfToken` | Не задан; необязательное значение cookie X `ct0` из той же сессии, используется вместе с `AuthToken` |
| `Parser:Headless` | `true`; браузер сбора работает без окна |
| `Parser:MaxScrolls` | `100`; лимит прокруток каждой из двух вкладок: профиль и ответы |
| `Parser:ScrollDelayMs` | `2000`; ожидание между прокрутками, минимум 500 мс |
| `Parser:MaxJobMinutes` | `20`; лимит времени одного задания |
| `Parser:MaxPhotoMegabytes` | `20`; прежний лимит загрузчика фотографий; сбор больше не вызывает загрузчик |
| `Parser:RetentionDays` | `null`; если задано положительное число, срок считается от первого сохранения поста |

Новые посты сохраняются без фотографий и сразу получают статус `Ready`. Ранее скачанные файлы остаются в `photos/<ключ>` вне репозитория и доступны через API. При повторном импорте старого поста со статусом `PendingPhotos` текст становится доступен без ожидания вложений; API возвращает только уже скачанные фотографии.

При включённом сроке хранения просроченные посты сразу исключаются из запросов. Фоновая очистка удаляет строки и ставит удаление файлов в устойчивую очередь. Сбой удаления файла не теряет задачу очистки. Изменение `RetentionDays` влияет на новые посты: существующие `ExpiresAt` автоматически не пересчитываются.

## HTTP API

JSON использует camelCase. ID постов X — строки; внутренние ID — UUID. Время — ISO 8601 с UTC/смещением. Период API `[from, to)`: начало включительно, конец исключительно, `from < to`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/health` | Доступность БД: 200 либо 503 |
| GET | `/openapi/v1.json` | Описание HTTP API |
| POST | `/api/parse-jobs` | Создать задание; ответ 202 и `Location` |
| GET | `/api/parse-jobs/{id}` | Статус, счётчики, ошибка, причина остановки |
| GET | `/api/parse-jobs/{id}/logs?page=1&pageSize=50&reason=TooShort` | Причины пропусков и неполных данных; `reason` необязателен, максимум 100 записей на страницу |
| POST | `/api/parse-jobs/{id}/cancel` | Идемпотентный запрос отмены |
| GET | `/api/authors` | Сохранённые авторы |
| GET | `/api/posts?authorId=...&from=...&to=...&page=1&pageSize=20` | Посты; максимум 100 на страницу |
| GET | `/api/posts/random?authorId=...&from=...&to=...` | Один случайный готовый пост |
| GET | `/api/photos/{id}` | Скачанная фотография готового непросроченного поста |

Тело создания задания:

```json
{"author":"username","from":"2026-01-01T00:00:00Z","to":"2026-02-01T00:00:00Z"}
```

Ответ поста содержит `id`, `sourceId`, `author`, `text`, `publishedAt`, `url`, `photos`. У новых постов `photos` пуст. Для ранее скачанных фотографий сохраняются `id`, `position`, относительный `url` API. Для их просмотра требуется тот же ключ API; WinUI читает их с сервера своим HTTP-клиентом.

Случайный выбор выполняется PostgreSQL среди подходящих ID через `random()`. Повторы при последовательных запросах допустимы. Нет постов — HTTP 404 с `code=no_posts_in_period`. Запрос не запускает сбор. Для больших объёмов потребуется измерить стоимость случайной сортировки.

Ошибки параметров — 400; отсутствующие объекты — 404. Предметные ошибки возвращаются в формате Problem Details с `code`, `title`, `detail`. Ошибки аутентификации — 401.

### Лог задания

В WinUI откройте вкладку **«Лог задания»**. ID текущего задания подставляется из вкладки сбора; можно вставить ID другого задания. Выберите причину и нажмите **«Обновить лог»**. Сводка показывает количество записей по каждой причине за всё задание, список — записи выбранной причины. Кнопки **«Назад»** и **«Далее»** переключают страницы по 50 записей. Во время сбора обновление выполняется этой же кнопкой.

Каждая запись содержит ID поста, автора, дату публикации, время записи в лог, число слов, фрагмент текста до 500 символов, код причины и пояснение. Из карточки можно открыть исходный пост в X. Изображения не скачиваются.

| Код причины | Значение |
| --- | --- |
| `WrongAuthor` | Автор поста не совпал с автором задания; в пояснении указаны оба |
| `OutsidePeriod` | Дата поста вне периода `[from, to)`; в пояснении указаны дата и границы в UTC |
| `TooShort` | В тексте меньше 10 слов; показано фактическое число слов |
| `Incomplete` | Неполный текст/метаданные или отсутствующий ID; учитывается как ошибка, `isError=true` |

Для одного поста сохраняется первая сработавшая причина в порядке проверок: автор → период → полнота данных → число слов. Уже сохранённые посты (`existing`) и повторы внутри прохода в лог пропусков не входят. Ошибка задания целиком остаётся в его `errorCode`/`errorMessage`.

API возвращает `items`, `page`, `pageSize`, `total` и `reasons` (массив `{reason, count}` по всему заданию). `total` относится к выбранному фильтру; записи упорядочены по возрастающему ID. `items` содержат `id`, `createdAt`, `sourceId`, `username`, `publishedAt`, `textPreview`, `wordCount`, `reason`, `detail`, `isError`. Неизвестная причина или неверная пагинация дают HTTP 400 с `code=invalid_log_query`, неизвестное задание — HTTP 404 с `code=job_not_found`. Используется обычная авторизация API.

Лог хранится в таблице `JobLogs`; миграция `AddJobLogs` применяется автоматически при запуске обновлённого API. Записи и счётчики пропусков сохраняются вместе. При восстановлении прерванного задания начинается новый проход: прежние записи этого задания очищаются одновременно со сбросом счётчиков. Логи завершённых заданий сохраняются после перезапуска, при удалении задания удаляются каскадно. Причины старых пропусков до обновления не восстанавливаются — для диагностики нужен новый сбор.

## Задания и источник

Состояния: `Queued`, `Running`, `CancelRequested`, `Cancelled`, `Completed`, `Failed`, `NeedsLogin`. Счётчики: `scanned`, `saved`, `existing`, `skippedVideo`, `skippedOther`, `errors`. Скачивание фото больше не выполняется и не влияет на счётчики задания.

Очередь хранится в PostgreSQL. Advisory lock выбирает один обработчик на БД. После перезапуска `Running` возвращается в очередь, `CancelRequested` завершается отменой. Сбор повторяется с начала, счётчики нового прохода сбрасываются; сохранённые посты не дублируются. `Completed` означает завершение прохода, а не полную историю автора. `errors > 0` означает частичный результат.

Playwright открывает профиль X, затем `/with_replies`, и читает структурированные ответы, которые загружает сама страница. Дубликаты между вкладками не увеличивают счётчик просмотренных. Это внутренний формат X, а не стабильный публичный API. `IPostSource` позволяет заменить источник. Видео и изображения браузером блокируются; сервер также не скачивает фотографии. Вложения определяются по метаданным, а не по расширению превью.

Минимум — 10 слов в сохраняемом тексте (ровно 10 принимаются). Слова считаются по буквам и цифрам Unicode; апостроф и дефис внутри слова не делят его, HTTP(S)-ссылки и отдельные emoji/знаки пунктуации не считаются словами. У репостов используется полный текст оригинала, у цитат — собственный текст цитирующего поста. Выбранный период и принадлежность автору по-прежнему проверяются. Короткие записи, записи вне периода и записи другого автора входят в `SkippedOther`; неполные данные — в `Errors`. `SkippedVideo` сохранён в API для совместимости со старыми заданиями; новые задания не отбрасывают посты из-за видео/GIF. Ранее сохранённые записи автоматически не удаляются.

Причины окончания: `NoMoreVisibleItems`, `ScrollLimit`, `SourceFinished`. Возможные ошибки: `login_required`, `source_unavailable`, `source_http_error`, `source_api_error`, `source_format_changed`, `rate_limited`, `job_timeout`, `processing_failed`. При `NeedsLogin` повторите серверный вход и создайте новое задание. Автоматического обхода ограничений X нет.

Перехват ленты распознаёт операции `UserTweets`, `UserTweetsAndReplies` и `UserOriginalsTimeline` по пути GraphQL на `x.com` и `api.x.com`, включая адреса без строки запроса. `UserOriginalsTimeline` используется страницей профиля для ленты исходных публикаций; её ответы обрабатываются тем же парсером постов. При нулевом результате сообщение `source_unavailable` различает отсутствие ответов ленты и отсутствие распознанных постов в полученных ответах. Оно показывает число карточек постов в DOM и имена/HTTP-статусы замеченных GraphQL-операций; те же сведения записываются в журнал сервера без cookie, заголовков авторизации и параметров URL. Частичный JSON-ответ с `data` и `errors` обрабатывается: доступные посты сохраняются. `source_api_error` означает, что X вернул непустой массив `errors` без распознаваемых постов даже при успешном HTTP-статусе; выводятся только числовые коды, без исходных сообщений ответа. Для диагностики приложите новый текст ошибки. HTML из «Просмотр кода страницы» может содержать только оболочку приложения: для анализа формата ленты нужен JSON из Network → Fetch/XHR → UserOriginalsTimeline (либо UserTweets/UserTweetsAndReplies) → Response.

**Ограничения:** полнота истории, доступность старых постов и текущая структура X не гарантируются. Профиль просматривается до лимита/остановки, период применяется к найденным записям. Не удалось распознать ни одного поста — ошибка, а не подтверждение пустой истории. Live-проверка требует вашей сессии X. Условия X ограничивают скрейпинг: [условия использования](https://x.com/en/tos).

## Подключение мобильного клиента

Swift использует тот же HTTP API через `URLSession`. На реальном телефоне `localhost` — сам телефон: для локального сервера нужен адрес компьютера. Перед доступом по сети задайте `Api:Key`, настройте прослушивание нужного адреса и HTTPS. Тестовый ключ в мобильное приложение для публичного распространения встраивать не следует; текущая схема рассчитана на частный тестовый клиент. Для публичного приложения потребуется пользовательская аутентификация.

При нескольких экземплярах API фотографии должны лежать в общем доступном хранилище. Первая версия ориентирована на один экземпляр сервера; внешняя очередь, объектное хранилище и автоматическое расписание сбора не добавлены.

## Тесты

```powershell
dotnet test tests/Parser.Tests
```

После установки Chromium дополнительную проверку запуска браузера и блокировки видео включает `$env:PARSER_BROWSER_TEST = '1'`. Без неё только эта проверка явно пропускается.

Без `PARSER_TEST_CONNECTION` интеграционные тесты явно пропускаются. Для полного прогона передайте строку подключения к **отдельному тестовому PostgreSQL**, где разрешено создание и удаление тестовых БД:

```powershell
$env:PARSER_TEST_CONNECTION = 'Host=localhost;Port=15439;Database=postgres;Username=parser_tests'
dotnet test tests/Parser.Tests
```

На Windows с PostgreSQL 17 можно воспользоваться [scripts/Test-Postgres.ps1](scripts/Test-Postgres.ps1): он создаёт временный кластер на loopback, запускает тесты и останавливает кластер. Существующие БД не изменяются; временные данные и журналы сохраняются для диагностики. Порт и путь к бинарным файлам задаются параметрами.

Тесты проверяют фильтрацию, даты и полный текст, сохранение постов без скачивания фото, повторный импорт старых `PendingPhotos`, выдачу ранее скачанных фотографий, HTTP API, случайный выбор, дубликаты, отмену, восстановление и срок хранения. Сбор с живого X не входит в автоматические тесты и требует отдельной проверки на авторизованной сессии.
